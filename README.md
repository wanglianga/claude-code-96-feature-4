# 出院后分级随访与高风险升级平台

面向术后出院患者的随访管理系统（纯前端单页应用，事件溯源内核）。系统基于**患者身份、手术类型、出院医嘱、过敏史、用药计划、既往随访记录**自动生成分级随访任务；患者通过受限入口上报症状/体温/血压/用药依从性/图片；护士、医生、药师按角色看到**不同字段并执行不同授权动作**。

## 一、一键启动（Docker）

```bash
docker compose up -d --build
# 浏览器打开 http://localhost:3001
# 健康检查： curl http://localhost:3001/healthz  → ok
```

停止：`docker compose down`。端口可用环境变量覆盖：`CC_PUBLISH_PORT=8080 docker compose up -d --build`。

镜像为多阶段构建（Node 构建 + 非 root nginx 运行，内部监听 8080），配置见 `Dockerfile` / `docker-compose.yml` / `nginx.conf`。

## 二、本地开发

```bash
npm install        # 安装依赖
npm run dev        # 开发服务器 http://localhost:5173
npm run typecheck  # TypeScript 类型检查
npm run build      # 生产构建 → dist/
npm run verify     # 领域引擎 65 项端到端自测（不依赖浏览器）
```

> 本项目为“前端”类型（有供用户完成业务操作的页面），按任务约定不提供 Swagger/OpenAPI。
> 数据保存在浏览器 localStorage，点页面右上角“重置数据”可恢复初始演示态。

## 四、已实现的核心能力与对应设计

### 1. 分级随访任务生成（`src/rules.ts → gradePatient`）
- 依据手术风险等级、出院医嘱（抗凝/血压/感染等）、过敏史、用药复杂度、高龄综合评分 → L1/L2/L3。
- L3 出院第 1/3/7/14/30 天，L2 第 1/7/14 天，L1 第 3/14 天自动排期。

### 2. 高风险规则 → 冻结普通自动随访 → 升级任务（`src/rules.ts → evaluateReport`，`src/engine.ts → submitReport`）
- 高危症状（呼吸困难、胸痛、伤口大量渗血等）、体温 ≥39℃、血压 ≥180/110 或 ≤90/50 等命中即升级；升级任务 2 小时 SLA。
- 升级创建时，所有未完成常规随访状态变为 **frozen（冻结，任务不删除）**；升级闭环后自动解冻；事件重开时重新冻结。
- 护士初筛三选一：**电话回访 / 急诊建议 / 转诊申请**。

### 3. 角色授权与字段脱敏（`src/rules.ts` 字段矩阵）
- 药师：姓名/电话/证件脱敏，不可见体温血压、伤口图片、完整诊疗医嘱；只能出具用药复核意见，引擎层角色守卫拒绝其写医嘱/转诊/闭环（`FORBIDDEN`）。
- 患者本人看本人档案为明文；护士/医生可见全部随访字段。时间线在药师视图下同样脱敏。

### 4. 四个关键边界情况的处理
| 边界情况 | 处理方式（可在时间线核对） |
|---|---|
| **新医嘱与既有随访计划冲突** | 医生补医嘱时自动检测冲突，勾选后旧任务状态置 `cancelled` 并写入 `supersededBy`（含原因+替代任务 id），可同时排定替代随访；旧任务保留不删除 |
| **患者在不同入口重复上报** | 小程序/短信/热线三入口；2 小时窗口 + 症状/体征内容指纹判重，重复条目标记 `duplicateOf` 且不重复建任务、不重复排队 |
| **医生补录时间早于护士记录** | 医嘱业务时间（occurredAt）可填过去时刻；系统记录时间（recordedAt）恒为当前。时间线按业务时间排序，补录条目标【补录】，原始记录不变 |
| **转诊未确认但患者再次恶化** | 恶化信息挂接在原转诊单 `pendingNotes`；系统拒绝创建第二张转诊单（`REFERRAL_EXISTS`）；转诊待确认时禁止闭环（`REFERRAL_PENDING`） |

其他：
- **撤回不改写历史**：医嘱撤回只追加 `order_withdrawn` 事件，原医嘱显示删除线与撤回原因；因错误医嘱被取消的随访生成“恢复随访”任务，旧取消事实仍保留。
- **闭环后再次恶化**：原升级事件 `case_reopened` 重开（旧关闭依据仍在时间线），不新建重复事件。
- **人工队列**：患者拒绝联系、授权过期、图片无法读取、中风险复核、通知失败均入队；同次上报多个原因合并为一个队列任务。
- **SLA 持续提醒**：高风险/人工任务超时后每次扫描产生递增序号的 `sla_reminder`（页面每 60 秒自动扫描，也可顶栏手动扫描/推进模拟时钟）。
- **异步通知失败**：通知走 outbox 模式，主流程不依赖通知成功；可在顶栏“模拟故障”，失败通知留痕并可重试，失败兜底转人工队列，杜绝漏随访。

### 5. 一致性保障（无重复转诊、无漏随访、无错误暴露）
- **命令幂等**：每条写命令带 `commandId`，同令牌重放（双击/网络重试/多入口）整体丢弃，返回零事件。
- **乐观并发**：按患者聚合版本号 `expectedVersion` 校验，两个角色基于旧页面并发提交时后到者收到 `CONCURRENT_CONFLICT`。
- **转诊唯一约束**：同一患者存在 requested/confirmed 转诊即拒绝再开。
- **事件溯源**：所有状态变更均为只追加事件（`src/types.ts` 的 24 种事件），实体状态由 `project()` 重放得到；时间线展示业务时间、记录时间、操作者、版本号、幂等键与原始 JSON 载荷。

## 五、建议的手工验证路径

1. 登录 `nurse`：左侧看到张建国“高风险·超时”、李秀兰“转诊待确认·恶化×1”、王桂芳“人工队列/授权过期”。
2. 选李秀兰 → 升级任务：再次点“转诊申请”会被唯一性规则拒绝；“追溯时间线”可见恶化挂接备注；尝试闭环被“转诊待确认”拦截。
3. 登录 `doctor` → 李秀兰“转诊确认”：确认后回护士页才能闭环。
4. 登录 `patient1`：用快捷场景①提交胸痛呼吸困难；切到 `nurse` 在“并发与幂等试验台”点“过期版本号再申请转诊”（应报 CONCURRENT_CONFLICT），再点“重放最近一次上报命令”（应零事件）。
5. 医生页给张建国补一条业务时间早于现在的医嘱（如“即刻停药并提前复查”），观察冲突任务的取消/替代关系；再撤回该医嘱，观察恢复性随访。
6. 登录 `patient3` 提交带损坏图片的上报 → 护士“人工队列”处置；重复从短信入口提交相同症状 → 上报记录显示“重复上报（已判重）”。
7. 顶栏“模拟故障”开启通知通道 → 护士发急诊建议 → “通知 Outbox”看到失败记录 → 恢复通道后“重新投递”成功。
8. 顶栏“+1h/+3h”推进时钟，观察超时任务持续增加提醒次数。
9. 登录 `pharmacist`：对比同一名患者，电话/体温/血压/图片字段消失，且页面没有任何医嘱/转诊/关闭入口。

## 七、目录结构

```
src/
  types.ts        领域类型与 23 种只追加事件定义
  rules.ts        分级规则/高风险规则/药物相互作用/字段脱敏矩阵
  engine.ts       事件溯源：提交(幂等+乐观锁)、投影、全部业务命令、SLA、时间线
  seed.ts         三名患者的初始演示场景（通过命令写入，保证事件一致性）
  store.ts        zustand 状态、localStorage 持久化、模拟时钟/通道故障
  components/     通用组件、患者横幅(脱敏)、事件时间线、医护布局
  views/          Login / Patient / Nurse / Doctor / Pharmacist 五个角色页面
verify/
  engine-check.ts 引擎端到端自测（npm run verify）
```
